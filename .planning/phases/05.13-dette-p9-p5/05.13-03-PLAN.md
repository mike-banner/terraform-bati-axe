# Plan 05.13-03 — P5 : Feedback loop « refus → remise au marché » testé

## What was done
- **`server/utils/handleLeadDecision.ts`** (nouveau) : orchestration de `decision.post.ts` extraite (même pattern que `handleStripeEvent`) — supabase injecté, logique pure testable. Retour typé `LeadDecisionOutcome` : `{ ok, relaunched, customerEmail }` ou `{ ok: false, reason: 'project_not_found' | 'lead_mismatch' }`. Étapes : résolution projet par token → appartenance du lead → écriture décision → (selected ⇒ stop) → `shouldRelaunch` + `canRelaunch` → leads engagés refusés en `lost` + `relaunch_count` incrémenté.
- **`server/api/v1/magic-link/[token]/decision.post.ts`** : réduit à un wrapper fin (zod → util → erreurs HTTP 400/403/404 → email de relance). Comportement identique.
- **`tests/unit/lead-decision.test.ts`** (nouveau, 9 cas) :
  1. Tous les engagés refusés (claim + free-grant) → `relaunched: true`, leads en `lost`, `relaunch_count` incrémenté.
  2. Un pro encore en attente → pas de relance.
  3. Décision `selected` → jamais de relance.
  4. Garde-fou : `relaunch_count` à `MAX_RELAUNCHES` → pas de relance.
  5. Aucun pro engagé → pas de relance.
  6. Lead d'un autre projet → `lead_mismatch` (403 côté HTTP).
  7. Token inconnu → `project_not_found` (404 côté HTTP).
  8. Erreur d'écriture de décision → throw.
  9. La décision est enregistrée sur le bon lead (`customer_decision: 'refused'`).
