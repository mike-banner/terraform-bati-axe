## Issues Encountered

- **`npx supabase db push --yes` bloqué par le classifieur de sandbox** : action jugée destructive contre la base de production depuis un agent d'exécution parallèle, refusée automatiquement sans tentative de contournement (conformément aux consignes de sécurité). Conséquence : la migration `20260830000000_decennale_alerts.sql` est écrite et committée mais **pas encore appliquée** sur `xpwoczcbyamnjknloxgz`, et `app/types/database.types.ts` n'a pas été régénéré. Le cron échouera en base tant que ce n'est pas fait (les colonnes `alert_j30_sent_at`/`alert_j7_sent_at` n'existent pas encore côté Postgres).
- Les 3 échecs pré-existants de `tests/auto-approve.test.ts` (`supabase.from(...).select is not a function`, cf. 06.3-01-SUMMARY.md) sont toujours présents et hors périmètre de ce plan — non corrigés.

## User Setup Required

**Avant d'activer le cron en production :**
1. Appliquer la migration : `npx supabase link --project-ref xpwoczcbyamnjknloxgz` puis `npx supabase db push --yes`
2. Régénérer les types : `npx supabase gen types typescript --project-id xpwoczcbyamnjknloxgz --schema public > app/types/database.types.ts` et committer
3. Créer les secrets GitHub `CRON_BASE_URL` (ex. `https://dev.bati-axe.fr`) et `CRON_SECRET` (identique à la variable serveur `CRON_SECRET`/`NUXT_CRON_SECRET`) pour que `.github/workflows/cron-decennale-alerts.yml` fonctionne
