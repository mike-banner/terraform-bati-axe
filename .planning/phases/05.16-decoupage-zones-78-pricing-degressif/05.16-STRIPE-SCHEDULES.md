# 05.16 — Comportement Stripe : gestion des zones actives

Référence technique du modèle de facturation par zones. À lire avant toute
modification de `server/api/v1/pro/zones/*` ou `server/utils/handleStripeEvent.ts`.

## Modèle

Un seul abonnement Stripe par pro (`pro_zones.stripe_subscription_id` identique
sur toutes les lignes actives). Pas de ligne Stripe par zone : un seul `price`
représente le tarif du palier total (1 à 4 zones), recalculé à chaque
changement de nombre de zones (`calculateZonePrice` / `zonePriceLookupKey`,
`server/utils/zoneMatcher.ts`).

Stripe n'autorise **qu'un seul Subscription Schedule actif à la fois** par
abonnement. C'est la contrainte structurante de tout ce qui suit.

## Les 4 actions possibles

| Action | Endpoint | Effet | Différé ? |
|---|---|---|---|
| Ajouter une zone | `zones/subscribe.post.ts` | Change le `price` de l'item existant, débit immédiat du prorata (`proration_behavior: always_invoice`) | Non — immédiat |
| Changer mensuel ↔ annuel | `zones/change-billing.post.ts` | Crée un Subscription Schedule à 2 phases (phase 1 = actuelle jusqu'à `current_period_end`, phase 2 = nouveau tarif) | Oui — fin de période payée |
| Retirer une zone (pas la dernière) | `zones/unsubscribe.post.ts` | Même mécanisme de schedule, phase 2 = tarif du palier restant | Oui — fin de période payée |
| Retirer la dernière zone | `zones/unsubscribe.post.ts` | `cancel_at_period_end: true` sur l'abonnement (pas de schedule) | Oui — fin de période payée |

## Garde-fou commun : `assertSubscriptionModifiable()`

`server/utils/zoneMatcher.ts`. Appelé en tête des 3 endpoints qui touchent
l'abonnement (`subscribe`, `change-billing`, `unsubscribe`). Bloque avec 409 si :

1. **`sub.cancel_at_period_end` est vrai** — l'abonnement est en cours de
   résiliation. On refuse toute modification plutôt que de faire payer un
   nouveau palier sur un service qui va s'arrêter quand même. Message :
   *"Réactivez-le via 'Gérer la facturation' avant de modifier vos zones."*
   Choix produit assumé : pas de réactivation automatique et silencieuse.
2. **`sub.schedule` existe déjà** — un changement (billing ou retrait de zone)
   est déjà programmé. Message générique, sans référence à une couleur de
   badge (les deux types de changement partagent ce même garde-fou).

Le front reproduit ces règles de façon préventive via le computed
`hasPendingScheduleAction` (`app/pages/espace/premium.vue`) : dès qu'il est
vrai, le toggle mensuel/annuel, la sélection de nouvelles zones et le bouton
"Retirer" sont désactivés — pour éviter d'atteindre l'API et de recevoir un
409 tardif.

## Distinguer les deux types de Subscription Schedule

`billing-change-status.get.ts` doit savoir si un schedule en cours est un
changement de facturation ou un retrait de zone, pour afficher le bon badge
(bleu vs orange) et le bon libellé. Le marqueur est la **metadata du
schedule** posée à la création :

```ts
await stripe.subscriptionSchedules.update(schedule.id, {
  phases: [...],
  metadata: { kind: 'zone_removal', zone_id, zone_name },
})
```

Absence de `kind` (ou `kind !== 'zone_removal'`) = changement de facturation
classique.

`cancel-billing-change.post.ts` (le lien "annuler" des deux badges) est
générique : `stripe.subscriptionSchedules.release(scheduleId)` fonctionne
pour les deux types, il ramène l'abonnement à sa phase actuelle sans jamais
appliquer la phase 2.

## Comment le webhook sait quelle zone a été retirée

Piège : au moment où Stripe applique la phase 2 d'un schedule de retrait de
zone, l'event `customer.subscription.updated` porte uniquement l'objet
**subscription** — pas le schedule. La metadata posée sur le schedule
(ci-dessus) est donc invisible à ce moment-là.

Solution : `unsubscribe.post.ts` pose **aussi** une metadata sur la
subscription elle-même :

```ts
await stripe.subscriptions.update(subscriptionId, {
  metadata: { pending_zone_removal_id: zone_id, pending_zone_removal_price: priceObj.id },
})
```

Dans `handleStripeEvent.ts` (`customer.subscription.updated`), on détecte que
la transition a eu lieu quand le `price.id` courant de l'item correspond à
`pending_zone_removal_price` : à ce moment précis, on passe **uniquement**
cette zone en `status: 'cancelled'`, puis on nettoie la metadata pour ne pas
rejouer le traitement sur les updates suivants.

Point d'attention : le webhook fait ensuite une mise à jour générique de
**toutes** les lignes `pro_zones` de cet abonnement (statut Stripe → statut
`pro_zones`, alignement `billing` sur l'intervalle du price). Cette mise à
jour générique doit exclure explicitement la zone qu'on vient de marquer
`cancelled`, sinon elle écrase ce statut avec `active` dans la même requête
webhook (`bulkUpdate.neq('zone_id', removedZoneId)`).

Si `cancel-billing-change.post.ts` annule un retrait de zone programmé, il
nettoie aussi cette metadata de subscription (sinon elle reste orpheline —
inoffensif mais sale, car le prix cible ne sera plus jamais atteint).

## Matrice des cas de conflit

| État actuel | Action tentée | Comportement |
|---|---|---|
| Rien en cours | N'importe laquelle des 4 | OK |
| Changement billing programmé (badge bleu) | Ajouter/retirer une zone, ou reprogrammer un changement billing | Bloqué (409 serveur + UI préventive) |
| Retrait de zone programmé (badge orange) | Changer de billing, ajouter une zone, retirer une autre zone | Bloqué (409 serveur + UI préventive) |
| Résiliation totale programmée ("Se termine le...") | N'importe laquelle des 4 | Bloqué — message dédié "réactivez d'abord" |

## Ce qui n'est PAS géré (limite connue)

- `pro_zones.price_cents` n'est pas recalculé sur les zones restantes lors
  d'un retrait (ni lors d'un changement de billing, d'ailleurs — c'était déjà
  le cas avant). Colonne informative, non lue ailleurs dans le code : pas
  bloquant, mais à corriger si un usage apparaît un jour.
- Pas de réactivation automatique d'un abonnement en cours de résiliation :
  décision produit explicite (voir garde-fou ci-dessus), pas un oubli.
