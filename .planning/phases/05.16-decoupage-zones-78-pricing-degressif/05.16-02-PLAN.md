# Plan Phase 05.16-02: Gestion des zones actives — retrait, résiliation, garde-fous multi-changements

## Contexte

05.16-01 a livré l'ajout de zones (immédiat, Stripe Checkout / mise à jour de
prix) et le toggle mensuel/annuel (Subscription Schedule). Il manquait le
retrait d'une zone — aucune UI ni endpoint ne le permettait, seule la
résiliation totale via le portail Stripe existait.

## Objectives

1. Permettre de retirer une zone individuellement, sans perdre les autres.
2. Afficher clairement jusqu'à quand la zone reste utilisable (période déjà payée).
3. Empêcher les conflits entre les 4 actions possibles sur un même abonnement
   (Stripe n'autorise qu'un seul Subscription Schedule à la fois).

## Proposed Tasks

- Task 1 : Endpoint `server/api/v1/pro/zones/unsubscribe.post.ts` — Subscription
  Schedule (comme `change-billing.post.ts`) si zones restantes, sinon
  `cancel_at_period_end` si c'était la dernière zone.
- Task 2 : `server/utils/handleStripeEvent.ts` — appliquer le retrait de la
  bonne zone au moment de la transition de phase, via metadata de subscription
  (le schedule n'est pas accessible depuis l'event `customer.subscription.updated`).
- Task 3 : `billing-change-status.get.ts` — distinguer schedule "changement de
  facturation" vs "retrait de zone" via metadata du schedule, exposer
  `pending_zone_removal`.
- Task 4 : `app/pages/espace/premium.vue` — bouton "Retirer" sur les cards de
  zone actives, modal de confirmation avec date de fin d'accès, badge orange
  de retrait programmé (lien "annuler" réutilisant `cancel-billing-change`).
- Task 5 : Garde-fou commun `assertSubscriptionModifiable()`
  (`server/utils/zoneMatcher.ts`) appliqué aux 3 endpoints de modification
  d'abonnement + reproduit côté UI (`hasPendingScheduleAction`) pour bloquer
  les combinaisons impossibles (cf. `05.16-STRIPE-SCHEDULES.md` pour la
  matrice complète).

## Verification Protocol

- Retirer une zone sur un abonnement à 2+ zones → badge orange avec date,
  zone toujours débloquée jusqu'à cette date, palier tarifaire recalculé au
  renouvellement suivant (vérifié via `stripe trigger` / webhook simulé).
- Retirer la dernière zone → `cancel_at_period_end` posé, mêmes garanties que
  la résiliation existante.
- Tenter une 2e action (billing, ajout, retrait) pendant qu'une est déjà
  programmée → bloqué avant l'appel API (UI) et par 409 (serveur) si forcé.
- Tenter une action sur un abonnement en cours de résiliation → bloqué avec
  message de réactivation.
