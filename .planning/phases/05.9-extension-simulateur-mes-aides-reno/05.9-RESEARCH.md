## Summary

L'API `https://mesaides.france-renov.gouv.fr/api/v1/` est réelle, publique, et a été testée en direct pendant cette recherche (appels `curl`/`python` effectués le 2026-08-18, réponses JSON réelles obtenues). C'est un moteur **Publicodes** (même famille que le simulateur impôts particuliers du gouvernement) exposé en API "conversationnelle" : on demande un ou plusieurs `fields` (chemins de règles Publicodes, ex. `eligibilite`, `PTZ.montant`, `gestes.chauffage.PAC.air-eau.montant`), on fournit une `situation` sous forme de paramètres de requête supplémentaires (`ménage.revenu.classe`, `logement.type`, etc.), et la réponse contient pour chaque champ demandé une valeur (`rawValue`/`value`) **et** la liste `missingVariables` des variables encore nécessaires pour affiner le calcul. Sans authentification, l'API a répondu HTTP 200 avec des données réelles à chaque test — un token existe (email à `mesaidesreno@anah.gouv.fr`) mais sert à la notification de changements, pas au contrôle d'accès de base constaté.

Deux découvertes changent des hypothèses du CONTEXT.md : (1) **CORS est ouvert** (`access-control-allow-origin: *` observé), donc le proxy Nitro D-03 n'est plus requis pour contourner CORS — mais reste justifié pour la gestion d'erreurs/logs côté serveur et pour ne jamais exposer un éventuel futur token au client ; (2) le mini-tunnel "revenu + composition du foyer" décrit dans le CONTEXT est **insuffisant** pour obtenir un résultat exploitable : l'API a aussi besoin du type de logement, période de construction, statut de propriété, code commune INSEE (pas le code postal), et idéalement DPE actuel/visé. Sans ces champs, `eligibilite` renvoie des `missingVariables` non vides et aucun montant fiable. Le repo source (`betagouv/reno`) est **archivé depuis avril 2026**, le service a été repris par l'administration (ANAH) sur le nouveau sous-domaine — le contrat API est stable en pratique mais sans garantie de versioning documentée.

**Primary recommendation:** Appeler l'API directement en HTTP (GET, query params) depuis le proxy Nitro — pas de package npm à installer (le module `mesaidesreno` npm est lié à l'ancien repo archivé, à éviter). Étendre le mini-tunnel aides au-delà de "revenu + foyer" pour couvrir les variables minimales d'`eligibilite`, et résoudre le code postal en code INSEE via `geo.api.gouv.fr` (gratuit, sans clé, déjà dans l'esprit des patterns gouv existants du projet type `recherche-entreprises.api.gouv.fr`).

## Architecture Patterns

### Flux recommandé (conforme D-03, D-04, D-05)

```
[mini-tunnel aides component]
  → recueille : revenu, personnes foyer, code postal, type logement,
    période de construction, statut propriétaire, (option) DPE actuel
  → POST/GET côté client vers /api/v1/aides-reno (Nitro, notre serveur)
       server/api/v1/aides-reno.get.ts (ou .post.ts)
         1. valider body avec Zod
         2. résoudre code postal → code INSEE via geo.api.gouv.fr (cache mémoire simple, ponytail)
         3. construire la query situation Publicodes (voir Code Examples)
         4. $fetch vers https://mesaides.france-renov.gouv.fr/api/v1?fields=eligibilite&fields=...
            avec timeout court (5-8s, l'API a répondu en ~1.9s lors des tests)
         5. si erreur/timeout → renvoyer { ok: false } (jamais throw 500 vers le client)
         6. si succès → parser rawValue des champs montant, calculer reste_a_charge
            = coût_travaux (computeEstimate()) - somme(aides.montant)
         7. renvoyer { ok: true, aides: {...}, reste_a_charge }
  ← composant affiche le bloc si ok:true, sinon message fallback (D-04)
  → au submit du lead existant (POST /api/v1/projects), injecter
    aides_estimees / reste_a_charge dans calculator_data JSONB (D-05)
```

### Pattern existant à réutiliser : proxy gouv côté serveur
`server/utils/siretLookup.ts` appelle déjà une API publique gouv (`recherche-entreprises.api.gouv.fr`) depuis Nitro avec gestion souple des statuts (`not_found`, `error` ne bloquent pas — cf. règle API-01 dans REQUIREMENTS.md). **Le même pattern de tolérance aux pannes s'applique ici** : ne jamais bloquer le flux principal sur une erreur d'API externe gouv.

### Anti-Patterns à éviter
- **Ne pas modifier `computeEstimate()`** ni son contrat (rappel CONTEXT) — le mini-tunnel aides est un calcul additif, pas un remplacement.
- **Ne pas envoyer le code postal brut à l'API Mes Aides Réno** en le faisant passer pour un code commune — l'API attend un code INSEE (ex: `'75056'` pour Paris), qui diffère structurellement d'un code postal (`75001`-`75020` mappent tous vers des arrondissements avec leurs propres codes INSEE ; certains codes postaux couvrent plusieurs communes).
- **Ne pas traiter les codes HTTP de l'API comme des indicateurs fiables d'erreur "utilisateur" vs "serveur"** — voir Common Pitfalls : l'API renvoie HTTP 500 aussi bien pour un champ mal orthographié que pour un paramètre manquant. Traiter tout non-200 comme "dégrader proprement", jamais tenter de distinguer types d'erreurs pour afficher un message spécifique à l'utilisateur.

## Don't Hand-Roll

| Problème | Ne pas construire | Utiliser à la place | Pourquoi |
|---|---|---|---|
| Résolution code postal → commune INSEE | Table statique CP↔INSEE maintenue à la main | `geo.api.gouv.fr/communes?codePostal=XXXXX` (gratuit, sans clé, officiel) `[VERIFIED: appel réel]` | Table déjà obsolète à la publication (fusions de communes) ; l'API gouv est à jour et gratuite |
| Calcul des aides/eligibilité MPR/CEE/Éco-PTZ | Réimplémenter les règles Publicodes MaPrimeRénov'/CEE en dur dans `calculateur.ts` | API Mes Aides Réno | Les barèmes changent chaque année (le doc officiel avertit explicitement que les infos CEE affichées sur ce service "sont datées" suite à des évolutions réglementaires) — un calcul maison serait faux plus vite qu'un appel API tenu à jour par l'État |
| Reste à charge | Chercher un champ `reste à charge` dans l'API | Calcul local = `estimate_min/max` (computeEstimate) − somme des `rawValue` montant des aides retournées | **Confirmé par test réel** : `?fields=reste à charge` renvoie une erreur 500 "référence introuvable" — ce champ n'existe pas dans le modèle Publicodes, il faut le calculer côté BÂTI-AXE |

**Key insight:** l'API externe fournit uniquement des montants d'aides unitaires par dispositif ; le "reste à charge" affiché à l'utilisateur est une donnée métier BÂTI-AXE (coût des travaux du calculateur existant moins somme des aides), pas une donnée native de l'API gouv.

## Common Pitfalls

### Pitfall 1 : Champ requête avec espaces dans les libellés JSON, mais dots sans espaces dans la query
**Ce qui piège :** Les réponses JSON affichent les chemins avec espaces autour des points (`"MPR . accompagnée"`, `"ménage . revenu . classe"`) — copier ce format tel quel dans les query params échoue silencieusement (l'API retourne 200 mais ignore le paramètre, la variable reste dans `missingVariables`).
**Pourquoi ça arrive :** Le format d'affichage JSON (labels lisibles) ≠ le format de requête réel.
**Comment l'éviter :** Utiliser les chemins **sans espaces** dans la query, ex. `ménage.revenu.classe='modeste'` (confirmé fonctionnel par test direct). Les valeurs textuelles (chaînes Publicodes) doivent être entourées de guillemets simples ou doubles littéraux dans la valeur du paramètre (ex. `'modeste'`, pas juste `modeste`).
**Signes avant-coureurs :** `missingVariables` contient toujours la variable qu'on pensait avoir fournie.

### Pitfall 2 : Toute erreur (syntaxe, champ manquant, champ inconnu) renvoie HTTP 500
**Ce qui piège :** Pas de distinction 400 (erreur client) vs 500 (erreur serveur) — un simple typo de nom de champ ou l'absence du paramètre `fields` renvoie systématiquement HTTP 500 avec un corps `{"error": "..."}`.
**Pourquoi ça arrive :** L'API ne fait pas de validation amont séparée du moteur de calcul Publicodes ; toute erreur d'évaluation de règle remonte comme une exception 500.
**Comment l'éviter :** Le proxy Nitro doit traiter **tout code non-200** comme "API indisponible pour ce lead" (D-04) — ne jamais tenter d'interpréter le corps d'erreur pour afficher un message différencié à l'utilisateur final, ne jamais faire confiance à un code 4xx qui n'arrivera probablement jamais dans les faits.
**Signes avant-coureurs :** Tests unitaires du proxy qui vérifient un statut 4xx spécifique — à éviter, tester plutôt "non-200 → fallback".

### Pitfall 3 : Repo source archivé, pas de garantie de stabilité contractuelle documentée
**Ce qui piège :** `betagouv/reno` est archivé depuis le 09/04/2026, le service a migré vers `mesaides.france-renov.gouv.fr` sous gestion ANAH avec un futur repo `github.com/anahgouv` annoncé comme "pas encore public" au moment de la recherche `[CITED: WebSearch beta.gouv.fr]`. Aucune politique de versioning/dépréciation n'est documentée sur la page `/api-doc`.
**Pourquoi ça arrive :** Transition d'un produit "beta.gouv" (startup d'État) vers une intégration officielle ANAH, en cours au moment de cette recherche (2026-08-18).
**Comment l'éviter :** Traiter cette intégration comme une dépendance externe volatile : timeout court, aucune logique métier bloquante dessus (déjà couvert par D-04), et prévoir de revalider le contrat (noms de champs, format des valeurs) si le service migre officiellement vers `anahgouv` GitHub dans les mois suivants.
**Signes avant-coureurs :** Changement d'URL de base, ou apparition d'un header `X-Api-Version` (mentionné dans les headers CORS autorisés, donc probablement utilisé en interne) qui deviendrait obligatoire.

### Pitfall 4 : Le CONTEXT sous-dimensionne les champs à collecter dans le mini-tunnel
**Ce qui piège :** Le CONTEXT.md décrit le mini-tunnel comme "revenu du foyer + composition" — insuffisant pour obtenir un `eligibilite` exploitable. Testé en direct : avec seulement revenu+personnes+type logement+statut propriétaire, `missingVariables` contient encore `logement . adresse`, `logement . commune`, `logement . propriétaire occupant`, `logement . résidence principale locataire`, `logement . période de construction`, `DPE . actuel`, `projet . DPE visé` pour plusieurs dispositifs.
**Pourquoi ça arrive :** Le modèle Publicodes MPR/CEE/PTZ a des règles d'éligibilité croisées (résidence principale vs secondaire, ancienneté du logement, DPE avant/après travaux) qui dépassent le simple couple revenu/foyer.
**Comment l'éviter :** Élargir le mini-tunnel à minima à : commune (dérivée du code postal existant), type de logement (maison/appartement), période de construction, statut propriétaire (propriétaire/acquéreur/non-propriétaire), "logement occupé comme résidence principale" (oui/non). Le DPE actuel/visé peut rester optionnel (dégrader vers une estimation moins précise plutôt que bloquer). **C'est une décision de scope à trancher avec le planner/l'utilisateur, pas juste une note technique** — voir Open Questions.
**Signes avant-coureurs :** Si le mini-tunnel ne pose que 2 questions et que le bloc "reste à charge" affiche systématiquement des montants à 0 € ou incomplets en test.

```json
    "type": "remboursement",

  },
  {
    "label": "Éco-prêt à taux zéro (éco PTZ)",
```

```
# Source: appel direct testé le 2026-08-18, geo.api.gouv.fr (officiel, gratuit, sans clé)
```

## Open Questions

1. **Le mini-tunnel doit-il couvrir plus que "revenu + foyer" (CONTEXT) pour produire des montants fiables ?**
   - What we know : testé en direct, revenu+foyer seuls laissent `missingVariables` non vide sur la plupart des dispositifs (MPR, PTZ, CEE) — les montants affichés seraient partiels/optimistes.
   - What's unclear : si le produit accepte d'afficher des montants "indicatifs, sous réserve" avec `missingVariables` non vide (mini-tunnel volontairement court, friction minimale), ou si la fiabilité prime (mini-tunnel plus long).
   - Recommendation : trancher avec l'utilisateur avant que le planner ne dimensionne les étapes du mini-tunnel — c'est un arbitrage produit, pas juste technique (impact direct sur combien de questions poser = combien de friction/abandon).

2. **SC-1 dit "avant révélation finale de l'estimation" alors que D-02 positionne le CTA aides APRÈS révélation (`revealed.value = true`).**
   - What we know : le CONTEXT est explicite et argumenté ("le lead principal est déjà capturé... zéro risque sur la conversion") — le mini-tunnel est un second parcours optionnel, pas une étape du tunnel principal.
   - What's unclear : la description de phase fournie en amont de cette recherche contredit littéralement ce point (SC-1 vs D-02). Le CONTEXT.md étant la décision utilisateur la plus récente et la plus détaillée, il doit primer, mais le planner doit noter explicitement cet écart pour ne pas re-designer par erreur le tunnel principal en croyant répondre à SC-1 à la lettre.
   - Recommendation : le planner traite D-02 (CONTEXT) comme la source de vérité, documente l'écart avec le libellé SC-1 dans son propre plan pour traçabilité.

### Known Threat Patterns

| Pattern | STRIDE | Mitigation standard |
|---|---|---|
| Abus du proxy `/api/v1/aides-reno` comme relais pour scanner/spammer l'API gouv externe | Denial of Service | Réutiliser le rate limiting Nitro déjà en place (INFRA-04, middleware sécurité mentionné dans REQUIREMENTS.md) sur ce nouvel endpoint |
| Injection de valeurs arbitraires dans les query params Publicodes transmis (ex. via `situation`) | Tampering | Ne jamais transmettre en pass-through brut les champs saisis par l'utilisateur — construire la query situation à partir d'un mapping fermé (whitelist de clés Publicodes connues), jamais `Object.entries(userInput)` direct vers l'URL externe |
