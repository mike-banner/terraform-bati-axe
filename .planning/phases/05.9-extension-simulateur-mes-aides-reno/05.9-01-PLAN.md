Contrat API externe vérifié en direct le 2026-08-18 (voir RESEARCH.md §Code Examples / §Common Pitfalls) :
- Base : `https://mesaides.france-renov.gouv.fr/api/v1`
- Requête : `GET ?fields=eligibilite&ménage.revenu.classe='modeste'&logement.type='maison'&vous.propriétaire.statut='propriétaire'`
  → clés SANS espaces autour des points, valeurs textuelles ENTRE guillemets simples dans la valeur du paramètre.
- Réponse : tableau JSON d'objets `{ label, fields, type, status, value, rawValue, missingVariables }`.
  `rawValue` = nombre exploitable pour les montants de subvention ; `type` = `remboursement`|`prêt`|... ; `status` = bool éligibilité ; `missingVariables` non vide = résultat incomplet.
- Aucun champ natif `reste à charge` : le calculer localement. Tout code non-200 (y compris 500 pour une erreur de champ) = API indisponible → dégrader (jamais interpréter le corps d'erreur).
- Résolution INSEE : `https://geo.api.gouv.fr/communes?codePostal=78000&fields=code,nom,codesPostaux` → `[{code:"78646",...}]` (peut renvoyer plusieurs communes → prendre le premier, dégradation acceptable).

Contrat `computeEstimate` (app/utils/calculateur.ts) : `{ estimate_min: number; estimate_max: number }` — le coût travaux est UNE fourchette, donc le reste à charge est lui aussi une fourchette.

Schéma actuel `calculator_data` (server/api/v1/projects.post.ts:18) — z.object STRICT qui strimpe les clés inconnues, donc les champs aides doivent être ajoutés explicitement.
Insert déjà `calculator_data: { ...data.calculator_data, trades }` (ligne 138) → les nouveaux champs validés seront persistés sans autre modification.
