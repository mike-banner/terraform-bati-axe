## Project Constraints (from CLAUDE.md)

- **ADR-004 (masquage serveur)** : sans objet direct ici (pas de données de prospect en jeu), mais le principe "ne jamais faire confiance au client" s'applique à la vérification de session recovery — ne jamais autoriser `updateUser({password})` sans une session Supabase réellement authentifiée (le SDK gère cela nativement, pas de contournement à construire).
- **Pattern route protégée (`useRequireAuth`)** : **NE PAS** utiliser ce composable sur `/pro/reinitialiser-mot-de-passe`. Cette page n'est pas une route "pro connecté normal" — elle doit accepter une session de type **recovery** (temporaire, obtenue via le lien e-mail) même si aucune session "normale" n'existe. Appliquer `useRequireAuth()` dessus la casserait (redirection vers `/pro/claim` avant que le SDK ait eu le temps d'échanger le code PKCE de l'URL). Cette page a besoin de sa propre logique d'attente de session (voir section Architecture Patterns).
- **Piège `watchEffect` + `navigateTo` sur `useSupabaseUser()`** : le même risque de course existe ici. Le SDK échange le code PKCE de manière asynchrone après le montage du client — il ne faut pas rediriger sur un `user.value` transitoirement `null` avant la résolution de cet échange.
- **Langue française** : tout le contenu des templates HTML, labels, messages d'erreur en français.
- **maxlength/pattern/type HTML cohérents avec Zod serveur** : cas particulier ici — `updateUser({password})` appelle directement l'API GoTrue via le SDK client, **sans passer par un endpoint Nitro custom**. Il n'y a donc **pas de schéma Zod serveur propre à ce champ** à faire correspondre. La contrainte HTML doit plutôt être alignée sur la règle déjà en vigueur ailleurs dans le projet (voir Pitfall "Incohérence de règle de mot de passe" ci-dessous), pas sur une contrainte Zod inexistante.
- **Commits sans mention IA, conventional commits en français** : respecter au moment de l'exécution.

## Summary

Le flux "mot de passe oublié" repose entièrement sur l'API native Supabase Auth (`resetPasswordForEmail` + `onAuthStateChange` + `updateUser`), sans nécessiter d'endpoint Nitro custom ni de table applicative. C'est un flux standard, bien documenté, avec protection anti-énumération native (l'appel ne révèle jamais si l'e-mail existe). Le point de vigilance principal n'est pas l'API elle-même mais (1) la bonne détection de la session de recovery côté client avec le SDK utilisé par ce projet (`@nuxtjs/supabase` → `@supabase/ssr`, flow PKCE par défaut, `?code=` en query string et non un fragment `#access_token`), et (2) le fait que le module d'auth du projet a déjà un piège connu et documenté (course `useSupabaseUser()` à l'hydratation) qu'il ne faut pas reproduire sur la nouvelle page.

Les templates Auth Supabase natifs sont un système entièrement séparé du moteur d'e-mail applicatif (`server/utils/email.ts` / `emailLayout.ts`) : ce sont des fichiers HTML statiques (Go template syntax, pas de JS, CSS inline obligatoire) référencés depuis `supabase/config.toml`, qui ne s'appliquent **qu'à l'instance locale**. La configuration équivalente en production doit être saisie manuellement dans le Dashboard Supabase (aucune commande CLI de type `config push` ne synchronise ces templates vers un projet hébergé — confirmé absent de la doc officielle).

**Blocker découvert pendant la recherche (à traiter avant/au début du planning) :** le CONTEXT.md de 06.4 présente `server/utils/emailLayout.ts` comme une dépendance déjà livrée par 06.3-01, mais **ce fichier n'existe pas sur le disque**. La phase 06.3 a été **planifiée** (4 PLAN.md committés, requirements EML-02..EML-10 formalisés) mais **jamais exécutée** — aucun SUMMARY, aucun fichier `server/utils/emailLayout.ts` ni `notifyAdmin.ts` dans l'arborescence actuelle. Seule une partie du périmètre 06.3 est réellement en place : `supabase/config.toml [auth.email.smtp]` (SMTP Resend) et un correctif dans `messages/index.post.ts`. La palette copper/navy et le texte du footer LCEN existent bien (documentés dans `06.3-01-PLAN.md`, section `<action>` de la Task 1), donc réutilisables **en dur** par 06.4 sans dépendre du code de 06.3-01 — mais le planificateur doit choisir explicitement : (a) dupliquer la palette/footer directement dans les templates HTML Supabase (recommandé, car ces templates ne peuvent de toute façon pas importer du TypeScript), ou (b) redemander l'exécution de 06.3-01 en préalable. Techniquement (a) est correct dans tous les cas car les templates Supabase ne peuvent jamais consommer `renderEmail()` (pas de runtime JS) — la dépendance réelle est donc seulement **documentaire** (recopier les mêmes valeurs hexadécimales et le même texte LCEN), pas une dépendance de code.

**Primary recommendation:** Implémenter le flux 100% côté client Nuxt avec le SDK Supabase existant (aucun nouvel endpoint Nitro, aucune nouvelle table), dupliquer en dur la palette copper/navy + footer LCEN dans 4 fichiers HTML statiques sous `supabase/templates/`, et documenter explicitement dans le PLAN la checklist manuelle "à configurer dans le Dashboard Supabase prod" pour ne pas laisser croire que la phase est "terminée" alors que seule la partie locale est branchée.

## Architecture Patterns

### Flux self-service — étapes exactes

1. **Déclenchement** (`/pro/claim`, formulaire login) :
```ts
// Source: https://supabase.com/docs/reference/javascript/auth-resetpasswordforemail [CITED]
const { error } = await supabase.auth.resetPasswordForEmail(email, {
  redirectTo: `${window.location.origin}/pro/reinitialiser-mot-de-passe`
})
```
- **Ne révèle jamais si l'e-mail existe** [CITED: supabase.com/docs/guides/auth/passwords] — `error` n'est renseigné qu'en cas de problème technique (rate limit, e-mail malformé), jamais pour "utilisateur introuvable". La UI doit donc **toujours** afficher un message neutre de succès ("Si un compte existe pour cet e-mail, un lien a été envoyé"), jamais une confirmation/infirmation d'existence.
- `redirectTo` doit être une **URL absolue** et doit correspondre au `site_url` ou figurer dans `additional_redirect_urls` de `supabase/config.toml` (actuellement `http://127.0.0.1:3000` / `https://127.0.0.1:3000` en local — même origine que l'app donc déjà couvert ; **en prod, vérifier que le domaine réel figure dans le Dashboard → Authentication → URL Configuration**, sinon Supabase rejette silencieusement la redirection).

2. **Réception du lien e-mail** : GoTrue génère une URL de type `{{ .ConfirmationURL }}` qui pointe vers `{SUPABASE_URL}/auth/v1/verify?token=...&type=recovery&redirect_to=...`. Après vérification côté GoTrue, l'utilisateur est redirigé vers `redirectTo` avec les paramètres de session.

3. **Détection côté client — point technique clé** : ce projet utilise `@supabase/ssr` (dépendance de `@nuxtjs/supabase`), dont le **flow par défaut est PKCE**, pas implicite [MEDIUM confidence — CITED doc officielle générale sur PKCE vs implicit, non vérifié spécifiquement sur la version exacte de `@nuxtjs/supabase` 2.0.10]. Concrètement :
   - Le lien final contient un paramètre `?code=...` en query string (pas un fragment `#access_token=...` comme dans l'ancien flow implicite).
   - Le client Supabase créé par `@nuxtjs/supabase` a `detectSessionInUrl` actif par défaut : à l'initialisation côté navigateur, il détecte automatiquement le `code` dans l'URL et l'échange contre une session — **aucun code d'échange manuel (`exchangeCodeForSession`) n'est à écrire**, contrairement aux setups Next.js/SSR qui exigent une route serveur `/auth/confirm`.
   - Une fois l'échange réussi, un événement `PASSWORD_RECOVERY` est émis via `onAuthStateChange` [CITED: supabase.com/docs/guides/auth/passwords].

4. **Page `/pro/reinitialiser-mot-de-passe`** — pattern recommandé (à écrire, **ne pas réutiliser `useRequireAuth()`**) :
```ts
// Ne PAS utiliser useRequireAuth() ici — cette page doit accepter une session
// "recovery" même en l'absence de session "normale" au premier rendu.
const supabase = useSupabaseClient()
const status = ref<'waiting' | 'ready' | 'expired' | 'success'>('waiting')

onMounted(() => {
  const { data: { subscription } } = supabase.auth.onAuthStateChange((event) => {
    if (event === 'PASSWORD_RECOVERY') status.value = 'ready'
  })
  // Filet de sécurité : si aucune session recovery n'apparaît après un court délai
  // (lien expiré/déjà utilisé/URL trafiquée), afficher l'état "expired".
  setTimeout(async () => {
    const { data: { session } } = await supabase.auth.getSession()
    if (status.value === 'waiting' && !session) status.value = 'expired'
  }, 2000)
  onUnmounted(() => subscription.unsubscribe())
})

async function submitNewPassword(password: string) {
  const { error } = await supabase.auth.updateUser({ password })
  if (error) { /* afficher erreur */ return }
  status.value = 'success'
  await supabase.auth.signOut() // éviter une session recovery persistante
  navigateTo('/pro/claim')
}
```
- **Lien expiré/déjà utilisé** : GoTrue renvoie une erreur dans l'URL de redirection elle-même (`?error=access_denied&error_code=otp_expired&error_description=...`) **avant** même que le SDK établisse une session — il faut donc aussi lire `route.query.error_code` au montage pour afficher un message clair ("Ce lien a expiré, demandez-en un nouveau") plutôt que de rester bloqué sur l'état `waiting`.
- **Gestion `otp_expiry` (3600s = 1h)** : c'est le délai de validité du lien de recovery, configuré globalement dans `[auth.email] otp_expiry` (partagé avec tous les types d'OTP — pas de valeur dédiée par type dans ce projet actuellement). Aucune action requise pour ce plan sauf documenter que **le lien expire après 1h** dans le texte du template e-mail lui-même.

### Anti-Patterns to Avoid
- **Réutiliser `useRequireAuth()` sur la page de reset** : ce composable redirige dès qu'aucune session "normale" n'est trouvée — il éjecterait systématiquement l'utilisateur avant que le SDK ait eu le temps d'échanger le `code` PKEC de l'URL.
- **Confirmer/infirmer l'existence d'un compte** dans le message affiché après `resetPasswordForEmail` (violerait la protection anti-énumération native de Supabase).
- **Importer `emailLayout.ts` ou toute fonction TypeScript de l'app dans les templates Supabase** : impossible techniquement (Go templates statiques, pas de runtime JS/Node) — dupliquer le HTML/CSS, ne pas chercher à "réutiliser le code".
- **Croire que `config.toml` suffit en production** : sans action manuelle dans le Dashboard Supabase (projet hébergé), les templates par défaut Supabase (non brandés, en anglais) resteront actifs en prod même après ce plan.

## Don't Hand-Roll

| Problème | Ne pas construire | Utiliser à la place | Pourquoi |
|---|---|---|---|
| Génération/validation de token de reset | Système de token maison (table `password_reset_tokens`, expiration, hash) | `supabase.auth.resetPasswordForEmail()` + `updateUser()` | GoTrue gère déjà la génération, la signature, l'expiration (`otp_expiry`) et l'invalidation à usage unique du token — le réimplémenter dupliquerait une fonctionnalité entière du serveur Auth |
| Protection anti-énumération d'e-mail | Vérifier soi-même si l'e-mail existe avant d'appeler l'API pour adapter le message | Rien — le comportement neutre est déjà natif à `resetPasswordForEmail()` | Toute vérification préalable côté app (ex. `SELECT ... FROM auth.users WHERE email = ...`) réintroduirait la fuite d'information que Supabase évite justement |

**Key insight :** Ce périmètre est délibérément "zéro backend custom" — la seule vraie complexité est l'UX (affichage des états waiting/expired/success) et le contenu des 4 templates HTML, pas la logique d'authentification elle-même.

## Common Pitfalls

### Pitfall 1 : Incohérence de règle de complexité de mot de passe
**Ce qui cloche :** `supabase/config.toml` fixe `minimum_password_length = 6` côté serveur Auth, alors que le formulaire d'inscription existant (`claim.vue`, `RE_PASSWORD = /^.{8,72}$/`) impose déjà 8 caractères minimum côté client, sans qu'aucun Zod serveur ne valide ce champ (l'appel passe directement par le SDK Supabase, pas par un endpoint Nitro).
**Pourquoi ça arrive :** deux couches de contrôle indépendantes (Supabase GoTrue vs. règle maison côté `claim.vue`) qui n'ont jamais été synchronisées.
**Comment l'éviter :** sur la nouvelle page de reset, reprendre exactement la même règle que `claim.vue` (`minlength="8" maxlength="72"`, même message "8 caractères minimum") pour rester cohérent avec ce que l'utilisateur a déjà vu à l'inscription — ne pas se caler sur les 6 caractères de `config.toml`. Signaler au planificateur que la vraie source de vérité pour la complexité de mot de passe (8 vs 6, complexité `password_requirements=""` actuellement vide donc aucune exigence de casse/chiffres) n'a jamais été tranchée explicitement par le client — c'est un candidat `[ASSUMED]`.
**Signes avant-coureurs :** un utilisateur crée un mot de passe de 6-7 caractères via un futur flux qui appellerait directement Supabase sans repasser par la règle UI de `claim.vue`.

### Pitfall 2 : Course de session à l'hydratation (déjà documentée dans CLAUDE.md, mais un piège légèrement différent ici)
**Ce qui cloche :** le pattern `useRequireAuth()` protège contre le `null` transitoire de `useSupabaseUser()` en réagissant à `getSession()`. Sur la page de reset, le risque inverse existe : `getSession()` peut renvoyer `null` **légitimement** pendant les premières centaines de ms, le temps que l'échange PKCE (`?code=...` → session) se termine en arrière-plan. Rediriger trop tôt vers `/pro/claim` casserait le flux pour un lien pourtant valide.
**Pourquoi ça arrive :** l'échange de code est asynchrone et non instantané, contrairement à une lecture de session déjà stockée en `localStorage`.
**Comment l'éviter :** utiliser `onAuthStateChange('PASSWORD_RECOVERY', ...)` comme signal principal (émis précisément quand l'échange aboutit), avec un délai de grâce (ex. 2s) avant de conclure à un lien expiré — voir code dans Architecture Patterns.
**Signes avant-coureurs :** en test manuel local, le lien Inbucket redirige bien vers la page mais celle-ci affiche immédiatement "lien expiré" alors que le lien vient d'être généré.

### Pitfall 3 : Rate limit d'e-mail réutilisé pour de l'auto-DoS
**Ce qui cloche :** `[auth.rate_limit] email_sent = 30` (porté à 30/h en 06.3 pour l'admin reset) et `[auth.email] max_frequency = "1s"` autorisent un renvoi quasi instantané. Un flux self-service public expose ce bouton "Mot de passe oublié" à n'importe quel visiteur non authentifié — sans cooldown UI, un clic répété épuiserait vite les 30 e-mails/heure partagés avec les autres usages Auth (invite, confirmation...).
**Pourquoi ça arrive :** ces valeurs de `config.toml` ont été dimensionnées en 06.3 pour un usage interne (reset admin uniquement, cf. commentaire dans le fichier), pas pour un flux public à volume potentiellement plus élevé.
**Comment l'éviter :** ajouter un cooldown côté UI (désactiver le bouton ~30-60s après un clic, message "Un e-mail a déjà été envoyé, réessayez dans une minute") — mitigation applicative simple, pas de changement de `config.toml` nécessaire pour ce plan.
**Signes avant-coureurs :** aucun test connu à ce jour — pitfall anticipé, pas observé.

### Pitfall 4 : Templates locaux confondus avec la config prod
**Ce qui cloche :** après ce plan, `supabase start` (local) affichera bien les templates brandés dans Inbucket — donnant l'impression que "l'e-mail de reset est fait" alors que la production continuera d'envoyer les templates par défaut Supabase (en anglais, non brandés) tant que personne n'a copié le même HTML dans le Dashboard.
**Pourquoi ça arrive :** `config.toml` + `content_path` ne s'appliquent qu'à l'instance CLI locale — confirmé absence de toute commande `supabase config push` équivalente pour l'auth email dans la doc officielle.
**Comment l'éviter :** le plan doit inclure une tâche explicite non-automatisée ("à faire manuellement avant le go-live") listant les 4 templates à copier-coller dans Dashboard Supabase → Authentication → Email Templates, avec le HTML final généré en 06.4.
**Signes avant-coureurs :** un pro reçoit un e-mail de reset en anglais/non brandé en prod alors que le dev local en local montrait un e-mail parfait.

## Security Domain

### Applicable ASVS Categories
| Catégorie ASVS | S'applique | Contrôle standard |
|---|---|---|
| V2 Authentication | oui | Flux natif Supabase Auth (`resetPasswordForEmail`/`updateUser`) — ne jamais construire de vérification de token maison |
| V3 Session Management | oui | Session de type "recovery" émise par GoTrue, courte durée d'usage prévue (appeler `signOut()` après le changement de mot de passe pour ne pas laisser traîner une session recovery) |
| V4 Access Control | non | Aucune ressource protégée par rôle n'est en jeu dans ce flux |
| V5 Input Validation | oui | `minlength`/`maxlength` HTML sur le nouveau mot de passe (8-72, cohérent avec `claim.vue`) ; e-mail déjà validé côté Supabase |
| V6 Cryptography | oui (délégué) | Le hachage du mot de passe est entièrement géré par GoTrue — ne jamais tenter de le reproduire côté app |

### Known Threat Patterns pour ce périmètre
| Pattern | STRIDE | Mitigation standard |
|---|---|---|
| Énumération d'utilisateurs via le formulaire "mot de passe oublié" | Information Disclosure | Comportement neutre natif de `resetPasswordForEmail()` (déjà en place, ne rien construire par-dessus qui le contournerait) |
| Abus du flux pour spammer un tiers (envoi répété d'e-mails de reset vers une victime) | Denial of Service | Rate limiting Supabase natif (`auth.rate_limit.email_sent`, `max_frequency`) + cooldown UI recommandé (Pitfall 3) |
| Interception/réutilisation d'un lien de recovery déjà utilisé | Tampering / Spoofing | Comportement natif GoTrue : un token de recovery est à usage unique — vérifier que le message d'erreur affiché ("lien déjà utilisé/expiré") ne redonne pas de session valide |
