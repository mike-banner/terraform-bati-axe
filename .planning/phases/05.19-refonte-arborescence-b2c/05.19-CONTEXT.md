## Implementation Decisions

### D-01 : Professional Types (Locked)
- **2 types seulement :** Spécialiste (coche 1-2 catégories, reçoit leads filtered) + Généraliste (reçoit tous)
- Généraliste = entreprise générale (peut s'auto-coordonner)
- Modèle tarifaire : Généraliste reçoit tout d'office, pas d'opt-in

### D-02 : Categories (Locked)
- **9 catégories** (anciennement 6, élargissement)
  1. Maçonnerie & Gros Œuvre
  2. Toiture
  3. Électricité
  4. Plomberie & Chauffage
  5. Peinture
  6. Isolation
  7. Carrelage
  8. Menuiserie (fenêtres, portes, parquet, **cuisine**)
  9. Rénovation Énergétique (PAC, solaire, géothermie)

### D-03 : Tunnel Étape 1 (Locked)
- **Multi-sélection** de catégories (au lieu de 1 seule) : particulier peut cocher Gros Travaux + Énergétique + Prestations simultanément
- 3 catégories affichées : "Gros Travaux" (renamed from "Rénovation Globale"), "Rénovation Énergétique", "Prestations Ciblées"

### D-04 : Tunnel Étape 2 (Locked)
- **Blocs distincts par catégorie** : si particulier coche [Gros Travaux, Énergétique], 2 blocs indépendants affichés (9+9 items max)
- Items filtrés par catégorie : pas les 26 d'un coup
- Gros Travaux : 2 sous-blocs (Gros Œuvre 3 items + Second Œuvre 6 items)
- Énergétique : grille 9 items + bandeau "coordination"
- Prestations : grille 11 items

### D-05 : Matching Logic (Locked)
- **Overlap rule :** Spécialiste reçoit lead si ≥1 item du projet ∈ ses catégories cochées
- **Généraliste :** reçoit tous les leads (aucun filter)
- **Cas spécial énergétique :** PAC/Solaire/Géothermie seuls → généraliste only (besoin coordination)
- Items "linkers" (ex: Électricité) peuvent matcher même seuls

### D-06 : Compatibility Matrix (Locked)
- **Implémentation :** Fichier TS `app/utils/workTypeMatrix.ts` (Option B — pas de table DB)
- Structure : `Record<string, CompatRule>` — chaque item a defaultRole, specialistMatches[], groupingStrategy
- Extensible partenaires sans revoir le core matching (ajouter colonnes partners, roles, etc.)
- **Pas de table `pro_groups`** — groupes implicites en UI seulement
- **Pas de matrice en DB** — logique applicative (matching en Nitro)

### D-07 : Schema Changes (Locked)
- `professionals` → ADD `professional_type` ENUM ('specialiste'|'entreprise_generale')
- `projects` → ADD `selected_category`, `selected_sub_category`, `selected_items TEXT[]`
- Migration unique, pas de table supplémentaire
- Compatibilité backwards : les 6 checkboxes existants restent inchangés

### D-08 : Non-Changes (Locked)
- ❌ Pas de table `pro_groups`
- ❌ Pas de fallback "Expert/MOE"
- ❌ Pas de webhook groupes
- ✅ Garder "Menuiserie" (inclut cuisine)
- ✅ 26 items du spec V1 inchangés (pas de renumérotation)

### Matrice de Compatibilité (workTypeMatrix.ts)
```typescript
export const COMPATIBILITY_MATRIX: Record<string, CompatRule> = {
  pac: {
    defaultRole: 'entreprise_generale',
    specialistMatches: [],
    label: 'Pompe à Chaleur',
  },
  salle_de_bain: {
    defaultRole: 'any',
    specialistMatches: ['carreleur', 'plombier'],
    groupingStrategy: 'implicit_team',
    label: 'Salle de Bain',
  },
  cuisine: {
    defaultRole: 'any',
    specialistMatches: ['menuisier'],
    groupingStrategy: 'single',
    label: 'Cuisine',
  },
  // ... 23 autres items
}
```

### Pseudo-code Matching (Nitro)
```typescript
// server/api/v1/leads/index.get.ts
const selectedItems = project.selected_items || []
const proCategories = pro.categories || []

if (pro.professional_type === 'entreprise_generale') {
  return true // reçoit tout
}

// Cas spécialiste
for (const item of selectedItems) {
  const rule = COMPATIBILITY_MATRIX[item]
  if (rule?.specialistMatches?.includes(proCategory)) {
    return true // overlap trouvé
  }
}
return false // aucun overlap
```

## Addendum 2026-10-09 — Révision modèle EGB (décision utilisateur, à faire valider par le client)
- **Spécialiste** : 1 à 2 métiers (liste unique des 9 catégories).
- **Entreprise Générale du Bâtiment (EGB)** : plusieurs métiers (jusqu'à 9) sur la même liste ; plus de cas « reçoit tout ». Elle ne reçoit que les chantiers recoupant les métiers cochés (même règle de recouvrement que les spécialistes). Validation admin (`egb_status`) toujours obligatoire avant toute réception ; le NAF reste un signal.
- **Nouveau métier ajouté plus tard** : jamais ajouté automatiquement (couverture décennale). Bandeau dashboard « Nouveau métier disponible » : chaque catégorie a une date `addedAt`, chaque pro un `categories_reviewed_at` ; boutons « Ajouter » (rappel décennale) / « Pas concerné ». Une seule source de vérité `PROFESSIONAL_CATEGORIES` importée par claim.post.ts, me.patch.ts, claim.vue.
- **Écarts du vérificateur à clore** : notifyMatchedPros (server/utils/notifyProLead.ts) aligné sur proMatchesProject + selected_items + egb_status ; UI admin de validation des EGB (consomme GET /api/v1/admin/egb et PATCH /api/v1/admin/egb/[id]).
- **Impact à reprendre** : effectiveProType / matching « EGB = tout » (workTypeMatrix.ts), alerte de coordination (postes réservés EGB), schémas Zod du claim, tests unitaires et e2e.
