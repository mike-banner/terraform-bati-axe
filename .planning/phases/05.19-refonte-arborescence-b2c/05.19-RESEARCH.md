## ⚠️ Avertissement — ce document remplace la V1, ne l'ignore pas

Une V1 de cette recherche existait déjà à ce même chemin (26 items fixes + `selected_items TEXT[]` en intersection directe avec `professionals.categories`, cf. `05.19-SPEC-ARBORESCENCE-B2C.md` marquée **« Spécification Validée »**). La demande V2 ("matrice de compatibilité" + "groupes de pros" + fallback "Je ne sais pas → Maître d'Œuvre") n'est pas une extension de la V1, c'est un **changement de mécanisme de matching** :

- V1 : `projects.selected_items` (26 slugs figés) ∩ `professionals.categories` (mêmes 26 slugs) → match direct.
- V2 : `projects.selected_items` → **table de correspondance** vers des "métiers" (Cuisiniste, Carreleur, Maître d'Œuvre...) qui ne sont **pas** les 26 slugs eux-mêmes, plus une notion de "groupe de pros" absente de V1.

**Les deux ne sont pas compatibles telles quelles.** Avant de planifier, il faut trancher explicitement laquelle des deux logiques est livrée (voir Recommandations #1). Le reste de ce document part du principe que V2 est la nouvelle direction demandée, mais le conflit avec la spec "Validée" doit être signalé à l'utilisateur — ce n'est pas à moi de le résoudre silencieusement.

## Constat Codebase (vérifié)

1. **`professionals.categories TEXT[]`** est peuplé par 6 checkboxes en dur (`app/pages/espace/profil.vue:150-181`) : `maconnerie`, `toiture`, `electricite`, `plomberie`, `peinture`, `isolation`. C'est le seul vocabulaire de matching qui existe aujourd'hui en base pour les pros.
2. **Le matching actuel est un array-contains simple**, pas une matrice : `server/api/v1/leads/index.get.ts:45` fait `.in('category', proCategories)` (le `category` du projet, singulier, legacy trade, doit être dans le tableau du pro) ; `server/utils/notifyProLead.ts:36` fait `.contains('categories', [category])`. Aucune notion de correspondance indirecte "type de travail → liste de métiers" n'existe dans le code — c'est une égalité directe de vocabulaire.
3. **Aucune table `pro_groups` ni notion de groupe de pros n'existe** dans les 40+ migrations du projet (`grep -rl "pro_groups\|professional_group" supabase/migrations/*.sql` → aucun résultat). C'est un concept entièrement nouveau.

## ⚠️ Collision de vocabulaire : "Architecte / Maître d'Œuvre" existe déjà, mais dans l'autre sens

C'est le risque le plus important trouvé dans cette recherche, à signaler avant toute planification.

`[VERIFIED: codebase]` — `app/types/b2b.ts` et `supabase/migrations/20260822000002_b2b_requests.sql` définissent déjà un type `B2bApporteurType = 'architecte' | 'bet' | 'agence_immo' | 'syndic' | 'diagnostiqueur' | 'autre'` (Phases 05.10/05.17/05.20 — "Espace Partenaires / Apporteurs d'Affaires"). Dans ce modèle existant :

- Un **architecte / bureau d'études (BET)** est un **apporteur de leads** (il amène un projet vers Bati-Axe via `/b2b/partenaires`, table `b2b_requests`) — flux **entrant**.
- La proposition V2 ("Je ne sais pas → proposer un Maître d'Œuvre / Bureau d'Études / Architecte disponible dans la base pour aider le client") demande l'**inverse** : un pro de type architecte/MOE qui **reçoit** un lead particulier comme n'importe quel artisan — flux **sortant**, symétrique aux artisans classiques.

Ce sont deux rôles opposés avec le même vocabulaire métier. Aujourd'hui :
- Il n'existe **aucun** architecte/MOE dans la table `professionals` (qui reçoit des leads) — seulement dans `b2b_requests` (qui en envoie).
- Créer un "pro Expert/MOE" qui reçoit des leads nécessite soit un nouveau type dans `professionals` (`professional_type` ou équivalent), soit un détournement du flux B2B existant — les deux sont des chantiers distincts non couverts par les phases 05.10/05.17/05.20.

**Recommandation :** nommer différemment ce rôle en base pour éviter la confusion avec `b2b_apporteur_type` (ex. `professional_type = 'expert_conception'` plutôt que réutiliser "architecte"), et documenter clairement dans le plan que c'est un rôle **sortant** (reçoit des leads comme un artisan) et non le rôle B2B **entrant** déjà existant. `[ASSUMED — nommage à valider avec le client]`

## Matrice de Compatibilité

### Deux implémentations possibles, tradeoffs différents

**Option A — Table Supabase `work_type_professional_mapping` :**
```sql
CREATE TABLE public.work_type_matrix (
  item_id TEXT NOT NULL,              -- slug de l'arborescence (ex: 'salle_de_bain')
  professional_type TEXT NOT NULL,    -- métier requis (ex: 'carreleur')
  is_primary BOOLEAN DEFAULT true,    -- métier principal vs. secondaire/optionnel
  PRIMARY KEY (item_id, professional_type)
);
```
Éditable sans déploiement (si un jour souhaité), interrogeable en SQL pour le matching (`JOIN` au lieu d'un lookup applicatif), mais ajoute une table + une requête au flux de dispatching qui n'existe pas aujourd'hui.

**Option B — Fichier statique TS (`app/data/workTypeMatrix.ts`), même pattern que le reste de l'arborescence :**
```typescript
export const WORK_TYPE_MATRIX: Record<string, string[]> = {
  salle_de_bain: ['carreleur', 'plombier', 'electricien'],
  cuisine: ['cuisiniste', 'carreleur', 'plombier', 'electricien'],
  // ...
}
```
Cohérent avec le choix déjà fait pour l'arborescence elle-même (V1, non remis en cause : "26 items = artefact de code, pas donnée éditable"). Zéro requête réseau supplémentaire, mais toute évolution de la matrice = déploiement.

`[ASSUMED]` — la matrice change probablement **moins souvent** que l'arborescence des travaux mais **plus souvent** que le schéma DB (ajout d'un nouveau métier = évolution produit fréquente selon la section "Ajout Futur de Métiers" du prompt utilisateur). C'est l'argument le plus fort pour l'Option A malgré le coût d'une table de plus — à confirmer avec le client si l'admin doit pouvoir éditer la matrice sans ticket dev.

### Ce que la matrice ne résout pas : le vocabulaire des métiers doit exister côté `professionals`

Que la matrice soit en DB ou en fichier statique, elle ne change rien au problème déjà identifié en V1 : `professionals.categories` contient aujourd'hui 6 valeurs (`maconnerie`, `toiture`, `electricite`, `plomberie`, `peinture`, `isolation`), pas les métiers détaillés de la matrice (`carreleur`, `cuisiniste`, `plombier`...). **Sans migration du formulaire `profil.vue` vers le nouveau vocabulaire de métiers, la matrice ne trouvera jamais de pro compatible** — c'est le même angle mort qu'en V1, non résolu par le passage à une matrice.

## Groupes de Pros

Concept entièrement nouveau, aucun pattern existant à réutiliser.

### Modélisation minimale

```sql
CREATE TABLE public.pro_groups (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  zone TEXT,                          -- cohérent avec professionals.zone (texte libre aujourd'hui)
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE public.pro_group_members (
  group_id UUID NOT NULL REFERENCES pro_groups(id) ON DELETE CASCADE,
  professional_id UUID NOT NULL REFERENCES professionals(id) ON DELETE CASCADE,
  PRIMARY KEY (group_id, professional_id)
);
```

Un groupe expose une "compétence collective" = union des `categories` de ses membres — pas de colonne dédiée, calculée à la lecture (`SELECT DISTINCT unnest(categories) FROM professionals WHERE id IN (SELECT professional_id FROM pro_group_members WHERE group_id = ?)`) pour éviter la désync entre un champ dénormalisé et les catégories réelles de chaque membre.

### Questions produit non tranchées (bloquantes pour planifier)

`[ASSUMED — aucune de ces réponses n'est dans le prompt utilisateur]` :
1. Un pro peut-il appartenir à plusieurs groupes ? (schéma ci-dessus le permet nativement, mais impact UX/tarifaire non précisé)
2. Le lead est-il débloqué **une fois pour le groupe** (un seul `leads.pro_id` = un ID de groupe fictif) ou **une fois par membre** (chaque membre du groupe unlock indépendamment le même `project_id`) ? C'est une décision qui touche directement `leads` (clé actuelle `(project_id, pro_id)` unique côté claim) et le modèle de facturation Stripe par abonnement — impact non négligeable, hors scope purement technique.
3. Qui décide qu'un groupe existe et qui en fait partie — un admin (back-office), ou les pros eux-mêmes (auto-organisation) ? Détermine s'il faut une UI admin (`AdminB2bTab`-like) ou une UI pro (`espace/profil.vue`-like).

Sans réponse à la Q2 en particulier, aucune tâche de plan ne peut être écrite pour le déblocage de groupe — c'est structurant, pas un détail d'implémentation.

## Ajout Futur de Métiers

Si la matrice est en table (Option A ci-dessus), ajouter un métier = une ligne `INSERT INTO work_type_matrix`, pas de migration de schéma, pas de déploiement — c'est l'argument central pour préférer une table à un fichier statique dans ce sous-domaine spécifique (contrairement à l'arborescence des 26 items en V1, qui elle reste un artefact de code figé).

Reste à trancher : `professional_type` sur `professionals` — aujourd'hui c'est un `TEXT[]` libre (`categories`), donc ajouter un nouveau métier ne nécessite **aucune migration DB** côté pro (pas d'enum Postgres contraignant les valeurs). C'est un avantage réel de l'architecture actuelle à préserver : ne pas remplacer `categories TEXT[]` par un `ENUM` qui figerait la liste des métiers au niveau schéma.

## Migration des 6 Catégories Actuelles (mapping)

`[VERIFIED: codebase]` — pas de mapping 1:1 propre possible, même constat qu'en V1 :

| Catégorie legacy | Métiers matrice candidats | Ambiguïté |
|---|---|---|
| `maconnerie` | `macon` | Faible — mapping direct plausible |
| `toiture` | `couvreur`, `charpentier` | Un pro "toiture" coché aujourd'hui ne dit pas s'il fait charpente ou couverture ou les deux |
| `electricite` | `electricien` | Faible |
| `plomberie` | `plombier` | Faible, mais "Plomberie & Chauffage" (libellé actuel) suggère aussi `chauffagiste` — non séparable rétroactivement |
| `peinture` | `peintre` | Faible |
| `isolation` | `isolation`, potentiellement `electricien` si PAC (cf. exemple du prompt) | Un pro "isolation" n'a jamais été qualifié sur PAC — ne pas déduire |

**Aucun mapping automatique fiable** ne peut peupler les nouveaux métiers détaillés (`carreleur`, `cuisiniste`, etc.) à partir des 6 valeurs actuelles — elles n'existent nulle part dans le vocabulaire legacy. Reset + re-sollicitation des pros existants reste la seule option honnête (même conclusion qu'en V1, renforcée par la granularité plus fine demandée ici).

## Cascade de Propositions

Flux demandé dans le prompt, confronté au code existant :

1. **Étape 1-2 (sélection + lookup matrice) :** réutilise directement l'arborescence V1 (26 items, déjà spécifiée et validée) comme source de `selected_items` — pas de nouveau chantier UI ici, la matrice se branche derrière, pas à la place.
2. **Étape 3a (groupe/collection de pros dispo) :** nécessite `pro_groups` (nouveau, voir ci-dessus) **et** un endpoint de matching qui n'existe pas — `/api/v1/leads` matche aujourd'hui pro par pro, jamais par groupe.
3. **Étape 3b (fallback "Expert") :** nécessite le nouveau rôle "reçoit des leads en tant qu'expert" — voir la collision de vocabulaire ci-dessus. Ce n'est **pas** le même objet que `b2b_requests.apporteur_type = 'architecte'`.
4. **Étape 4 (signature avec l'expert OU sélection individuelle) :** hors scope technique de cette recherche — c'est un parcours de conversion/paiement (Stripe ? devis ?) non décrit dans le prompt, à clarifier avant planification (`[ASSUMED — aucune indication sur le modèle économique de l'étape 4]`).

## Recommandations

### 1. Faire trancher le conflit V1/V2 avant tout — c'est la question prioritaire
La SPEC validée décrit une intersection directe de 26 slugs. Cette recherche V2 décrit une matrice indirecte + des groupes. **Un plan ne peut pas satisfaire les deux en même temps sans clarification.** Deux issues possibles à proposer au client : (a) la matrice V2 remplace le matching direct de la SPEC V1 (la SPEC doit être amendée, pas juste la recherche) ; (b) la matrice V2 est une V-suivante distincte, hors scope de 05.19, et cette phase reste sur le plan V1 déjà validé. Je recommande (b) pour limiter le risque — la SPEC "Validée" représente un accord client déjà obtenu, la réouvrir sans passer par une nouvelle validation explicite serait un chantier de refonte, pas une correction.

### 2. Matrice : table Supabase (Option A), pas fichier statique
Contrairement à l'arborescence (V1, non remise en cause), la matrice métier est plus volatile (le prompt utilisateur anticipe explicitement des ajouts de métiers fréquents) — une table permet l'édition sans déploiement si un besoin admin apparaît, pour un coût de requête négligeable (une jointure de plus au moment du dispatching, pas au chargement du Step 1 particulier).

### 3. Renommer le rôle "Expert/MOE côté artisan" pour ne pas collisionner avec `b2b_apporteur_type`
Utiliser un identifiant distinct (`professional_type = 'expert_conception'` ou similaire) plutôt que réutiliser "architecte"/"bureau d'études" tels quels — ces libellés désignent déjà un rôle opposé (apporteur, pas receveur) dans le module B2B existant (05.10/05.17/05.20).

### 4. Groupes de pros : ne pas construire avant d'avoir tranché le déblocage (unitaire vs. collectif)
C'est une question de modèle de facturation/abonnement (Stripe), pas de schéma DB — proposer le schéma minimal (`pro_groups` + `pro_group_members`) mais ne pas écrire de tâches de plan pour le flux de claim/unlock tant que la Q2 (ci-dessus) n'est pas répondue par le client.
